# 07 — Design the tool registry + MCP client bridge

Type: grilling
Status: resolved
Blocked by: 01, 03

## Question

Design the **tools seam** and its **guarded execution pipeline**, plus the **MCP client bridge** — the plug surface the user cares most about ("tool/MCP integration points").

Decide:

- **The tool registry** (`ctx.tools`) — scoped per-agent registration, tool schema assembly into the system prompt, and how a model-facing tool is defined (definition, schema, execute body).
- **The guarded execution pipeline** — porting `docs/tool-execution-pipeline.md`: the `tools/pre-execute` → monotonic guards → `tools/execute` → `tools/post-execute` waterfalls, approval seam (`ctx.approval`), result normalization, `finalizeContent`, `tools/result`.
- **The MCP client bridge** — the settled direction (client, consume external servers into `ctx.tools`): which MCP spec version(s), transports (stdio/HTTP), JSON-RPC framing, and how external MCP tool schemas map onto `ctx.tools` schemas. Decide the protocol surface the spec locks and what a first bridge targets.

Consume `01-seam-inventory` (tools/mcp seam listed as core) and `03-rust-runtime` (how the waterfalls and approval map to the typed-event runtime).

## Answer

Resolved by grilling (1 round, all recommendations accepted) with the dev. The tools seam + guarded pipeline + MCP client bridge design the spec must document. Consumed the runtime (03), the seam inventory (01), and dsh refs (`docs/subsystems/tools.md`, `docs/tool-execution-pipeline.md`, `packages/mcp/mcp-client/README.md` + its `@modelcontextprotocol/sdk ^1.12.0` pin).

- **Q1 — ToolDefinition, full-fidelity.** Reproduce `ToolDefinition`: the model-facing `ToolSchema` (name/description/parameters) plus a mandatory `output` canonical declaration (JSON-Schema + pure `render` + optional `presentationMeta`), an `execute(args, exec) -> Promise<unknown>` returning only canonical lossless-JSON, and optional `finalizeContent` (total, must-not-throw, runs exactly once per normalized outcome including pipeline failures), `timeoutMs` (cooperative, wrapped by a `tools/execute` policy), `isConcurrencySafe` (pure classifier), `presentCall`/`presentResult` (pure UI projection — deferred, web UI out of scope, but the fields exist). The registry's `schemas()` builds the model-facing projection via an explicit **allowlist** (name/description/parameters only) — output/execute/finalizeContent/timeout/isConcurrencySafe/presenters never leak to the model. `execute` receives `args: unknown`; first-party tools use a `defineTool`-style typed builder that validates/narrows. Registration is a trusted same-process contract validated at load.
- **Q2 — Scoped registration & ToolRestriction.** Reproduce per-scope tool filtering over inherited (global + ancestor) tools: `ToolRestriction { allow?, deny? }` compiles to private name sets, intersections applied across the scope chain, then the scope's OWN registrations overlaid (exempt). Deny-only admits later unlisted inherited tools; allow-list excludes them. Maps to the runtime's `isolate` scope: "give one session a different capability set."
- **Q3 — Guarded execution pipeline.** `ctx.tools.execute(input)` materializes parsed args once into a pipeline-owned `ToolExecution` (deep-frozen, caller `signal`), then runs: **`tools/pre-execute`** waterfall (reorderable allow/deny/ask) → **registered monotonic guards** (deny-or-abstain, identity-protected, cannot be reordered around) → **`tools/execute`** (around-dispatch wrappers: timeout/retry/metrics; only this view may replace the required signal) → **`tools/post-execute`** waterfall (accept/block/replace/add-context) → optional definition-owned **`finalizeContent`** → **`tools/result`** (synchronous emit, frozen authoritative outcome). `ctx.approval` is the one-shot permission seam dispatched over its `approval/request` waterfall; absent/unanswerable → deny (`unavailable`), fails closed. Result normalization: a pipeline/`execute` throw becomes `isError` with structured error identity; the registry snapshots the candidate result losslessly before `finalizeContent`. `ToolRunContext` provides `deferContext(...)` (nested-dispatch channel, appended after `tool/result`) and `concludeTurn()`. Scheduling: `ToolExecutionMode { parallel | exclusive }` — the loop forms exclusive barriers and a bounded rolling parallel pool. Mapped to the runtime's five dispatch modes: the three `tools/*`-pipeline stages and `approval/request` are waterfalls (next()-veto); `tools/result` is `emit`.
- **Q4 — Tool schema DSL.** A Rust unified JSON-value schema DSL (`ValueSchemaSpec`): string/number/integer/boolean/null/array/object/json/oneOf, object nodes with explicit `additionalProperties`, scalar `enum`/`const`, parameter requiredness as per-property annotation. Compiles to JSON Schema for the model wire and validates args + canonical output at runtime. Exact in Rust (the 16-level TS inference bound is a TypeScript artifact). Parameter error → `INVALID_ARGS`; invalid body/post-policy value → output error.
- **Q5 — MCP client bridge protocol surface.** Target the MCP spec as implemented by the TypeScript SDK **1.12** (modern MCP: **stdio** + **streamable-http**, JSON-RPC 2.0 framing). In Rust, back it with a maintained Rust MCP client (e.g. **`rmcp`**). The `ctx.mcp` seam (existence + crate pinned in 03, `dsh-mcp`) owns the client transports + protocol; the bridge registers discovered tools onto `ctx.tools` under server-qualified names `mcp__<serverName>__<rawName>`. **Tools-only** bridge: Resources and Prompts have no harness consumer, deferred — matching dsh.
- **Q6 — MCP bridge lifecycle.** Reproduce dsh's behavior: on connect, wait `listTools()` and register under public names before the first turn (`failOnStartupError` governs whether activation rejects vs. activates tool-less); listen `notifications/tools/list_changed` → re-sync (a generation swap — never a partial set; a registration conflict rolls back the whole attempted generation). Public names are pure functions of `(serverName, rawName)`, normalized to the 64-char `[A-Za-z0-9_-]` contract with a deterministic 12-hex hash appended on collision/truncation. Execute via `callTool({name: rawName, arguments}, {signal})` with the configurable `toolCallTimeoutMs` (default 60000); the public name never leaves the process. Disconnect → supervisor restart with exponential backoff (initial doubling to max; budget resets after maxDelay uptime; `maxAttempts` consecutive failures → unregister + stop). Canonical success is `{ content: JsonValue[], structuredContent? }`; supported advertised `outputSchema` validates `structuredContent` (unsupported vocabulary → unconstrained `JsonValue`). Rendering preserves MCP block order; images enter durable core blocks only when `ctx.attachments` is mounted and the route explicitly supports image input (audio/embedded/resources → explicit diagnostics, not loss).

**Spec locks:** Q1–Q6. **Deferred:** resources/prompts bridging, image-attachment persistence breadth (depends on `ctx.attachments`/web being deferred), UI presenters (web UI out of scope), compaction of tool results. Sources: `docs/subsystems/tools.md`, `docs/tool-execution-pipeline.md`, `packages/mcp/mcp-client/README.md`; runtime design from 03; seam list from 01.
